# TECH_ARCHITECTURE.md — MOLTEN CROWN

> Struktura math + frontendu, kompletny kontrakt eventów, data flow.
> Kod: `math/` (Python), `frontend/` (TypeScript). Kontrakt zweryfikowany testami.

---

## 1. Wysokopoziomowy data flow

```
                    ┌──────────────────────── Stake Engine RGS ───────────────────────┐
  Player URL  ─────▶│  /wallet/authenticate  /wallet/play  /wallet/end-round  /bet/event │
  (sessionID,       └──────────▲───────────────────────┬──────────────────────────────┘
   lang, device,               │  Book {id, events[],  │  payoutMultiplier}
   rgs_url)                     │                       ▼
                    ┌───────────┴───────────┐   ┌───────────────────────────────┐
                    │  Frontend (TS/Pixi)   │   │  Published math library        │
                    │  RgsClient ─▶ BookPlayer│  │  index.json + lookup CSV +     │
                    │  BookPlayer ─▶ Presenter│  │  books_*.jsonl.zst  (per mode) │
                    └───────────────────────┘   └───────────────▲───────────────┘
                                                                 │ generated by
                                                 ┌───────────────┴───────────────┐
                                                 │  Math engine (Python)          │
                                                 │  GameConfig ▸ GameState ▸ run  │
                                                 │  optimizer ▸ publish ▸ analysis│
                                                 └────────────────────────────────┘
```

Zasada nadrzędna (SDK): **eventy są jedynym źródłem prawdy dla frontendu.**
Frontend **nie liczy** payoutów — odtwarza je z `payoutMultiplier` / eventu `finalWin`.

## 2. Math layer — struktura (`math/`)

```
math/
├── engine/                 # reusable (game-agnostic)
│   ├── symbols.py          # ranks, ore variants, paytable, next_symbol
│   ├── rng.py              # seeded deterministic RNG (replay)
│   ├── board.py            # fill, components, wild-attach, fusion(+rank jump), gravity
│   ├── events.py           # Book + event builders (the contract, source of truth)
│   ├── config.py           # Config / BetMode / Distribution (SDK-shaped)
│   ├── optimizer.py        # max-entropy weight tilt + pinned max-win prob
│   ├── publish.py          # index.json + lookup CSV + books.jsonl.zst (exact format)
│   └── analysis.py         # weighted stats, buckets, feature contribution
├── game/                   # game-specific (Molten Crown)
│   ├── game_config.py      # paytable, drop-weights, bet modes, Heat caps
│   ├── gamestate.py        # spin resolution, Forge Fury, Molten Core, max-win clamp
│   ├── run.py              # generate ▸ optimize ▸ publish ▸ analyse (CLI)
│   └── forced_outcomes.py  # labelled reproducible QA catalogue
├── tests/                  # test_forge / test_events_schema / test_rtp / test_maxwin
└── publish_files/          # generated output (index.json, lookup, books)
```

Separacja: `engine/` = logika wielokrotnego użytku; `game/` = reguły konkretnej gry.
Zgodne konceptualnie z oficjalnym `StakeEngine/math-sdk` (`src/` ↔ `engine/`,
`games/<id>/` ↔ `game/`), więc gra jest portowalna do oficjalnego SDK.

## 3. Frontend layer — struktura (`frontend/`)

```
frontend/
├── src/
│   ├── types/events.ts     # kontrakt eventów (1:1 z events.py)
│   ├── rgs/params.ts       # sessionID/lang/device/rgs_url z URL (nie hardkodować)
│   ├── rgs/RgsClient.ts    # authenticate/balance/play/end-round/event + błędy
│   ├── game/BookPlayer.ts  # odtwarzanie eventów (skip/resume), zero obliczeń
│   ├── game/Presenter.ts   # interfejs prezentacji (Pixi/DOM/headless)
│   ├── audio/AudioManager.ts # warstwy, ducking, priorytety SFX
│   └── main.ts             # wiring: auth ▸ resume ▸ spin ▸ end-round
└── player/                 # runnable, self-contained replay harness (DOM presenter)
    ├── build_player.py     # wstrzykuje realne książki z forced/catalog.json
    └── index.html          # otwórz w przeglądarce — replay bez build-stepu
```

**Rozdzielenie logiki i prezentacji:** `BookPlayer` (logika przepływu) ↔ `Presenter`
(rysowanie). Produkcyjny renderer PixiJS + Svelte implementuje `Presenter`; harness
DOM w `player/` implementuje ten sam interfejs — dowód, że kontrakt jest kompletny.

## 4. KONTRAKT EVENTÓW (kompletny)

Każdy event: `{ "index": int, "type": str, ...pola }`. `index` rośnie 0..n‑1.
Runda zawsze kończy się `finalWin` → `roundEnd`. `payoutMultiplier == finalWin.amount×100`.

| # | type | pola | znaczenie | animacja frontendu |
|---|---|---|---|---|
| 1 | `revealBoard` | `board`, `heat`, `spinKind`(base/free/super), `scatters` | nowa plansza spinu | opad rudy |
| 2 | `anticipation` | `scatters`, `needed` | teaser triggera (2 Cindery) | pulsacja, duck audio |
| 3 | `forge` | `fusions[]`, `heat` | grupy fuzują o rangę wyżej | rozżarzenie→zlanie, Heat+1 |
| 4 | `gravity` | `spawned[]`, `board` | opadanie + refill | drop nowych komórek |
| 5 | `heatUpdate` | `heat` | zmiana Heat (poza forge) | wskaźnik Heat |
| 6 | `settleWin` | `relics[]`, `baseValue`, `heat`, `win` | wypłata spinu | count‑up, podświetlenie |
| 7 | `bonusStart` | `mode`(forge_fury/molten_core), `spins`, `kind` | wejście do bonusu | transition, baner |
| 8 | `spinCounter` | `remaining`, `total` | licznik spinów | HUD |
| 9 | `retrigger` | `added`, `spins` | +spiny w Forge Fury | „+N”, błysk |
| 10 | `superSeed` | `board`, `minRank` | pre‑seed planszy (super) | „wykuwanie” |
| 11 | `lockUpdate` | `locked[]`, `vault` | bankowanie do Vault (super) | relikwia→Vault |
| 12 | `pour` | `vault`, `heat`, `win` | kulminacja super | Wylew lawy |
| 13 | `totalWinUpdate` | `totalWin` | suma rundy | HUD total |
| 14 | `maxWin` | — | osiągnięto cap 15,000× | pełnoekranowy finał |
| 15 | `finalWin` | `amount` | ostateczna wygrana rundy | podsumowanie |
| 16 | `roundEnd` | — | koniec rundy | odblokowanie next |

Pola złożone:
```jsonc
// fusions[] element:
{ "from": <sym>, "to": <sym>, "cells": [[r,c]...], "wildCells": [[r,c]...],
  "anchor": [r,c], "value": <float x> }
// spawned[] element: { "r":int, "c":int, "sym":<sym> }
// relics[]/locked[] element: { "r":int, "c":int, "sym":<sym>, "value":<float x> }
```
Symbole (`sym`) = int id (patrz `frontend/src/types/events.ts` / `symbols.py`).

**Wznowienie rundy (resume):** `authenticate` zwraca aktywną rundę → `BookPlayer.play()`
odtwarza eventy od początku (stan wynika z eventów). `auto_close_disabled=True` dla
bonus/super umożliwia dokończenie przerwanej rundy nawet przy payout 0.

## 5. Kontrakt RGS (klient) — zweryfikowany z docs

| Endpoint | Request | Response (kluczowe) |
|---|---|---|
| `POST /wallet/authenticate` | `{sessionID}` | `{balance, config{minBet,maxBet,stepBet,betLevels,jurisdiction}, round}` |
| `POST /wallet/balance` | `{sessionID}` | `{balance}` |
| `POST /wallet/play` | `{sessionID, amount, mode}` | `{balance, round{book, mode}}` |
| `POST /wallet/end-round` | `{sessionID}` | `{balance}` |
| `POST /bet/event` | `{sessionID, event}` | `{event}` |

- Pieniądze: int × 10⁶ (1,000,000 = 1.0). Waluta = tylko display.
- `mode` ∈ {base, ante, bonus, super}; debit = `amount × cost_multiplier`.
- Błędy: `ERR_VAL/IPB/IS/ATE/GLE/LOC/GEN/MAINTENANCE` → mapowane w `RgsClient`.
- `jurisdiction.disabledTurbo/disabledFullscreen/socialCasino` sterują UI.

## 6. Format publikacji (zweryfikowany, egzekwowany przez `publish.py`)

- `index.json`: `{"modes":[{name,cost,events,weights}]}` (ściśle 4 klucze).
- `lookUpTable_<mode>.csv`: wiersze `uint64`: `sim_id, round_probability(weight), payoutMultiplier`.
- `books_<mode>.jsonl.zst`: po jednej książce na linię `{id, events, payoutMultiplier}`, zstd.
- `payoutMultiplier` = int (1150 = 11.5×).

Faktyczny `index.json` (wygenerowany):
```json
{ "modes": [
  {"name":"base","cost":1.0,"events":"books_base.jsonl.zst","weights":"lookUpTable_base.csv"},
  {"name":"ante","cost":1.25,"events":"books_ante.jsonl.zst","weights":"lookUpTable_ante.csv"},
  {"name":"bonus","cost":100.0,"events":"books_bonus.jsonl.zst","weights":"lookUpTable_bonus.csv"},
  {"name":"super","cost":500.0,"events":"books_super.jsonl.zst","weights":"lookUpTable_super.csv"} ] }
```

## 7. Wydajność (frontend)

- Mobile‑first; `Presenter` abstrahuje renderer (Pixi w prod), co pozwala na
  degradację efektów (reduced motion / słabsze GPU) bez zmiany logiki.
- Zalecenia prod: texture atlases, ograniczenie draw calls, lazy‑load ciężkich
  assetów bonusu/super, kompresja audio, brak alokacji w pętli animacji, pooling
  cząstek. Portrait/landscape/desktop layouty przez CSS/kontener.
- Skip: `BookPlayer.skip()` skraca bieżącą animację (wynik niezmienny).

### 7.1 Pomiar (ZROBIONE — wykonany, nie szacowany)

Profil CPU klatki bezczynnej (Chromium headless, CDP `Profiler`, 6 s, próbka
200 µs): **99,9 % czasu poza JS**, w rasteryzacji. Koszt klatki skaluje się z
LICZBĄ PIKSELI kanwy niemal dokładnie — 3,1× więcej pikseli kosztowało 3,05×
więcej czasu. Renderer jest więc ograniczony fill‑rate'em, nie CPU.

Środowisko pomiaru: kontener BEZ GPU (ANGLE/SwiftShader, rasteryzacja
programowa). Liczby bezwzględne NIE przenoszą się na urządzenia graczy —
przenosi się kształt zależności.

| konfiguracja (viewport 1280×800, SwiftShader) | mediana klatki |
|---|---|
| stan wyjściowy: tier 0, filtry stale podpięte, 9 warstw tła | ~1285 ms |
| tier 1 (bez post‑processingu) | ~1273 ms |
| tier 3 (kanwa 640×369, bez post‑processingu) | ~425 ms |
| tier 3 + `antialias: false` (pomiar rozpoznawczy) | ~344 ms |
| **stan końcowy: tier 3 + ukryte warstwy alpha‑0** | **~257 ms** |

Wnioski:

(a) Same filtry NIE były dominującym kosztem (tier 1 dał ~1 %), ale trzy
pełnoekranowe przebiegi render‑target na klatkę przy zerowym efekcie były czystą
stratą — `syncFilters()` podpina je dopiero gdy realnie coś robią.

(b) Jedyną skuteczną dźwignią jest liczba pikseli — stąd `PerfGuard`.

(c) **Pixi rysuje sprite'y o `alpha = 0`.** Test widoczności w
`collectRenderablesMixin` czyta `globalDisplayStatus` (visible/renderable/
measurable) i nigdy alpha. Tło trzyma 3 sceny × 3 plany = 9 pełnoekranowych
warstw, z czego widoczne są 3 — sześć rasteryzowało się co klatkę, żeby nie być
widocznym. Ustawienie `visible = false` poza cross‑fade'em ścięło klatkę z
~425 ms do ~257 ms (‑40 %). To zysk na KAŻDYM tierze i na prawdziwym sprzęcie
także, nie tylko w rasteryzacji programowej.

(d) MSAA kosztuje ~20 % klatki, dlatego `antialias` włączamy tylko przy
`devicePixelRatio < 1.5`, gdzie piksel urządzenia jest na tyle duży, że
schodkowanie widać.

### 7.2 `PerfGuard` — degradacja jakości

Mierzy czas klatki własnym zegarem (`Ticker.deltaMS` jest przycinane do
`maxElapsedMS` = 100 ms, więc cały interesujący zakres byłby niewidoczny).
Okno zamyka się po 45 klatkach LUB po 1500 ms przy min. 4 klatkach — im wolniejsze
urządzenie, tym szybciej zapada decyzja. Mediana > 40 ms (25 fps) → krok w dół;
mediana > 160 ms → dwa kroki naraz.

| tier | co gasi |
|---|---|
| 1 | post‑processing + ruch ambientowy (`lowPower`) |
| 2 | render w 3/4 rozdzielczości |
| 3 | render w 1/2 rozdzielczości (podłoga: 0.5) |

Degradacja jest JEDNOKIERUNKOWA — strażnik, który też podnosi jakość, oscyluje
(schodzi, klatki wracają *bo* zszedł, wraca w górę). Jakość wraca przy kolejnym
załadowaniu strony. Layout nie zależy od rozdzielczości: `renderer.width/height`
są w jednostkach logicznych, a `autoDensity` utrzymuje rozmiar CSS kanwy.
Zweryfikowane w źródle Pixi: `TextureSource.resize` bez argumentu rozdzielczości
zachowuje bieżącą (`resolution || this._resolution`), więc obrót ekranu nie
cofa degradacji.

Testy: `frontend/tests/perfguard.mjs` (25 asercji) — zegar i ticker
wstrzykiwane, więc reguły są sprawdzane na czasach klatek dyktowanych przez test,
a nie przez czekanie, aż maszyna zwolni.
